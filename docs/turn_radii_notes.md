A current weakness of our drawing of corners between legs, is that our drawings assume an instantanius turn to the new heading as we pass over the waypoint. In reality that isn't possible. In reality we're doing to describe a radius as we make the turn. This radius would be dependent on the speed we're going, and the G we're going to pull for the turn. For certain aircraft there may even be degree-per-second limitations due to radar systems. This turn will always start at the point we overfly the given waypoint.

This G for a turn should be an optional term in the config yaml. Default it to 2G (a seemingly sensible middle ground)
This should now give us a radius that our aircraft will turn immediately after hitting a waypoint, to get onto a heading to hit the next WP. Likewise an overriding degree-pers-econd field should also be an optional term in the config yaml. Default to no angular/time limit. The speed for a turn will be the considered to be the speed for the leg the turn immediately follows.

The following descriptions will be described from the perspective of a leg, at the end of which we make our turn, setting outselves up for the next leg. Due to this arc requiring space, we in effect give ourselves a new start point for calculations of the *next* leg. "Current Waypoint" refers to the waypoint we're just passing and turning immediately afterwards. "Next Waypoint" refers to the desintation waypoint of the next leg.
This arc would be described by placing an imaginary circle of our turn radius touching the current waypoint. If our next waypoint is left of our leg's track, the circle would be placed so our leg is tangent to the circle, on the left side of the leg, with the tangent point at the current waypoint position. The circle is similarly placed on the right side if the next waypoint is right of the leg.
On this imaginary circle, there is then another tangent point along the circle, that points directly at the next waypoint. Note, the heading of the line at this tangent point will very likely be different to the previously calculated direct WP to WP heading for the next leg. This second tangent point will then be the point from which things like the MC, the current leg's NMC, and card orientation will be based from. The arc from the current WP to this tangent point need to be factored in to the next leg's distance, ToT and fuel, and other downstream calculations. This may require a multiple pass solution if these small changes in leg length force a change in leg speed to keep a ToT.

Leg track lines that are currently drawn directly from WP to WP, will instead need to be drawn from the aforementioned 2nd tangent point, to the next waypoint. 
Furthermore the arc along the circle, from the current WP to this tangent point should also be drawn. Eventually we will only want to show the sections of the arc that lay beyond the boundary of the circular, triangular or square waypoint markers. But initially for debugging we will want to see the entire thing drawn, to confirm it's working correctly and for debugging. So this should be easily adjustable in the code (no need for it in the config.yaml)

The end result should be that a leg should be drawn and calculated from it's start point, to it's desintation WP, and then describe an arc to face towards the next waypoint. If this does not make sense, or there are any clarifying questions you need answering, ask them.
